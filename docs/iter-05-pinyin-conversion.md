# 工作记录 iter-05：拼音转汉字的能力测评

日期：2026-11-27。涉及 `52hz-models`（`experiments/` 下的脚本）和 `52hz-docs`。数据是 `iteration-003` 里没有噪声的子句。编号约定见[迭代记录](iterations.md)。

## 问题

iter-04 把 harness 里的缺陷修了一遍，一次成功率从 24.4% 到 26.7%。但损失的大头一直是模型第一次写出的那句话：即使按键完全没有敲错，整句全对的也只有 51%。

在这之前，所有设计都默认“模型会把拼音转成汉字”，把噪声当成唯一的难点。这个默认没有验证过。本迭代只测这一件事：给模型一段完全正确的拼音序列，它能转得多准，在哪里失败，和拼音的写法有多大关系。不带噪声，不经过校验和回路。

两个指标分开看：

- **整句全对**：输出和标准答案逐字相同。它同时受标准答案质量的影响，比如口语写法、人名、原文的错别字。
- **往返一致**（round trip）：输出的读音和输入的拼音完全一样，多音字按任一读音算。它只衡量转换本身，和标准答案无关。

## 目标

这一轮是测评，不是调分。做到下面四条就算完成：

1. **把“正确的拼音 → 汉字”测到没有悬念。** 每种可行的做法在 1000 条干净子句上的往返一致率和整句全对率，带置信区间：输入形态、指令、示例、上文、约束解码、采样投票、定点重问。
2. **剩余的失败说得出原因。** 逐类分清哪些是这个模型做不到的，哪些是标准答案自己的问题（口语写法、人名、错别字）。
3. **给出一个可以放进正式流程的提议级配置**，带它在干净输入上的数字和延迟。最终选定的配置要在另一批没用于挑选的干净子句上再量一次。
4. **回答“这个模型够不够用”。** 不够的话，差在哪一类上。

不在这一轮里的：带噪声的输入（下一轮把结论搬过去）、换模型或量化版本（Q7，需要下载，另议）、改正式流程的代码。

## 怎么推进

按[迭代规范](iterations.md#迭代规范)走环路。这一轮的 benchmark 是 1000 条干净子句上的往返一致率和整句全对率。每一步都是：提出假设 → 用最小的实验能否定它 → 先在 353 条上快速看（两三分钟）→ 有希望再上 1000 条确认 → 记下结果、观察到的问题和改动 → 提交并推送 → 下一步。

- 实验一律串行，长跑之前先用两三条请求走通整条链路并核对输出。
- 测评里发现的明显问题（脚本丢字符、输入形态和分词器不对齐这类）直接改掉并重跑；会改变解码方式的做法（约束解码、采样投票）只记为建议，附数字。
- 不下载模型。遇到需要决定的事就停下来，把问题和选项记在“待办”里。
- 连续两个变体的差别落在噪声范围之内，就不再往下加变体。

## 现象

正式流程对干净输入的最终结果，试跑集加验证集共 353 条：

| 结果 | 占比 |
|---|---|
| 全对 | 51.0% |
| 读音相同、成词、上下文也分不出（容忍层） | 13.0% |
| 读音相同、成词，但上下文其实能定 | 7.4% |
| 同音但不成词，或把正确的拼音读成了别的 | 13.0% |
| 多一个字或少一个字 | 6.5% |
| 离标准答案很远 | 2.8% |
| 被拦下 | 6.2% |

- 上屏的文字按字算 91% 是对的。有上文时全对 54%，没有上文 33%。新闻、百科、知识型对话约 64%，两个闲聊语料 33%–41%。
- 逐音节看，音节错误率是 4.2%：2027 个音节错了 86 个。一句 12 个音节，每个音节约 96% 正确，整句全对就只有六成左右。51% 就是这么来的。
- 出错时多数只错一个音节：86 处差异里 44 处是单个音节被换成了别的，22 处是多一个或少一个音节，9 处是连续几个一起错，那才是真正不成话的。位置均匀分布，前、中、后三段各约四分之一。

所以问题不是长句到后面崩掉，而是逐音节对齐的精度不够：每个音节都有约 4% 的概率看走眼，`lai` 看成 `li`，`dao` 看成 `de`。

下面这几条的输入都是正确的全拼，输出却读不回输入：

```text
输入      nilaiwodianlidagongba
标准答案  你来我店里打工吧      ni lai wo dian li da gong ba
输出      你离我点里大工吧      ni li  wo dian li da gong ba

输入      wozaigeinidaigeshenmejijuxiexiaolongxiashenmede
标准答案  我再给你带个什么寄居蟹小龙虾什么的    … ji ju xie xiao long xia …
输出      我在给你带个什么积木谢小龙下什么的    … ji mu xie xiao long xia …
```

这类错误校验器看得见，读音和按键有出入。但额度至少容 2 个错，所以它们被放行上屏了。

## 原因

### 连写拼音和模型的分词器不对齐

同一句拼音的两种写法，模型的分词器切出来的 token：

```text
连写        nilaiwodianlidagongba
        →   nilai | w | odian | lid | ag | ong | ba

按音节分开  ni lai wo dian li da gong ba
        →   ni | lai | wo | dian | li | da | g | ong | ba
```

连写时 token 的边界横跨音节，模型拿到的是一串没有意义的字母块，要自己重新对齐；分开后基本一个 token 一个音节。这是 round trip 差的直接原因。

### 模型零样本几乎不会转连写拼音

353 条干净输入，只看首次回复，不带校验和回路：

| 提示词 | 整句全对 | 往返一致 |
|---|---|---|
| 裸提示，连写 | 22（6%） | 48（14%） |
| 裸提示加上文，连写 | 32（9%） | 47（13%） |
| 13 个示例，连写 | 105（30%） | 144（41%） |
| 裸提示，按音节分开 | 105（30%） | 171（48%） |
| 裸提示加上文，按音节分开 | 100（28%） | 149（42%） |
| 示例，只给分开的音节 | 131（37%） | 179（51%） |
| 正式流程的提示词 | 167（47%） | 232（66%） |

- 只把拼音按音节分开，不带任何示例，就从 6% 到 30%，往返一致从 14% 到 48%。它比 13 个示例带着连写拼音还高。
- 正式流程的提示词是目前最好的：连写和分开的音节都给，并且写明“每个字都要对得上按键的读音，不增字不删字”。只给分开的音节反而更低，所以指令的严格程度也是一个因素，后面的测评把两者分开量。
- 带上文没有帮助，往返一致反而略降：模型会顺着上文把句子改得更通顺，偏离了拼音。

### 提示词里“可能有按键错误”的提醒不是原因

我最初的假设是：提示词提醒模型“可能有按键错误、没有标记的地方也可能漏了字母”，让它对干净的输入也到处找错。数据不支持：带这句提醒是 105 条全对，不带是 107 条，逐条比 6 对 4，p = 0.75。

## 被否定的假设

- **提醒“可能有按键错误”会伤干净输入。** 没有差别。
- **只给按音节分开的拼音最好。** 连写和分开都给、加上逐字对应的规则更好（47% 对 37%）。

## 测评方案

在 1000 条干净子句上系统地测（`clean-1000.jsonl`：从 benchmark 的 5000 条无噪声子句里按来源和长度抽，五个来源各约 200 条，长度四档均匀）。长度刻意均匀，所以它的总体数字不能直接和 benchmark 的比。每个结果跑 1000 条，置信区间约 ±3%。

| 问题 | 做法 | 结果决定什么 |
|---|---|---|
| Q1 给模型完全正确的音节，它能转多准 | 按音节分开的拼音，裸提示 | 提议这一级的天花板 |
| Q2 声调有多大帮助 | 带声调数字、带声调符号两种写法 | 帮助大，说明瓶颈在辨音。日常用不上，但能定位原因 |
| Q3 指令、示例、上文各起多大作用 | 严格指令对比最简指令；带示例对比不带；带上文对比不带 | 提示词该带什么 |
| Q4 在哪里失败 | 对失败的案例逐音节比对，按长度、来源、多音字、生僻字、人名分 | 改进该针对哪一类 |
| Q5 约束能不能从结构上保证往返 | 按音节限定可用的汉字（语法约束解码） | 能的话往返问题彻底解决，要看延迟的代价 |
| Q6 指出错处再问一次能修回多少 | 对读音和输入不一致的位置定点重问 | 干净输入上的回路该怎么做 |
| Q7 是不是量化的影响 | 换一个量化版本对比，需要下载，另议 | 要不要换模型文件 |

llama.cpp 有通用的语法约束解码，但我没有查到它有现成的拼音约束语法，所以 Q5 是“可以试、还没验证”。

## 结果

每一轮按[迭代规范](iterations.md#迭代规范)记三件事：结果是什么、观察到了什么问题、修改了什么。

### 第 1 轮：输入形态、指令、示例、上文

**结果。** `clean-1000`，1000 条干净子句，只看模型的首次回复。往返一致率是主指标。

| 变体 | 往返一致 | 整句全对 | 音节错误率 | 中位耗时 |
|---|---|---|---|---|
| 带声调符号，裸提示 | 706（**70.6%**） | 512（51.2%） | 2.4% | 353 ms |
| 正式流程的提示词 | 618（**61.8%**） | 410（41.0%） | 5.8% | 492 ms |
| 分开 + 严格指令 + 示例 + 上文 | 573（57.3%） | 396（39.6%） | 3.6% | 344 ms |
| 分开 + 严格指令 + 示例 | 516（51.6%） | 295（29.5%） | 5.3% | 336 ms |
| 分开 + 严格指令 | 515（51.5%） | 262（26.2%） | 4.6% | 325 ms |
| 分开，裸提示 | 417（41.7%） | 208（20.8%） | 5.7% | 346 ms |
| 带声调数字，裸提示 | 293（29.3%） | 126（12.6%） | 9.7% | 360 ms |
| 连写 + 严格指令 | 119（11.9%） | 57（5.7%） | 14.8% | 331 ms |
| 连写，裸提示 | 86（8.6%） | 43（4.3%） | 18.9% | 366 ms |

“分开”是按音节分开，“严格指令”是正式流程里那句“每个字都要对得上读音，不增字不删字，不改写、不概括”，“示例”是正式流程的 13 个示例。正式流程的提示词是连写和分开都给，加上严格指令、示例和上文。整句全对的 95% 置信区间约 ±3 个百分点。

和正式流程逐条比：带声调符号是往返一致修对 236、改坏 148；只给分开的音节加上其余全部，是修对 142、改坏 187（p = 0.015），整句全对没有差别（118 对 132，p = 0.41）。

正式流程的提示词按条件分：

| | 往返一致 | 整句全对 |
|---|---|---|
| 4–8 字 | 78% | 56% |
| 9–14 字 | 65% | 40% |
| 15–20 字 | 51% | 33% |
| 21–30 字 | 51% | 33% |
| 有上文 | 64% | 44% |
| 没有上文 | 50% | 26% |
| 新闻、知识型对话 | 71%、68% | 54%、54% |
| 网页文本和两个闲聊语料 | 59%、57%、53% | 41%、27%、29% |

**观察到的问题。**

1. **输入形态是主因。** 同样是裸提示，连写 8.6%，按音节分开 41.7%。
2. **严格指令有用，示例和上文各管一件事。** 严格指令让往返一致从 41.7% 到 51.5%。示例对往返一致没有帮助（51.5% 到 51.6%），对整句全对有（+3 个百分点）。上文对两者都有帮助（往返一致到 57.3%）。
3. **连写和分开都给，比只给分开好。** 往返一致高 4.5 个百分点。所以正式流程里那行切分提示不该取代连写的按键，该和它并列。
4. **模型不擅长的是不带声调的拼音。** 带声调符号、什么都不带，就超过正式流程 9 个百分点；音节错误率 2.4%，其余变体都在 4% 以上。声调写成数字反而更差（29.3%）。用户不打声调，这条路用不上，但它把瓶颈定位到了“同一个音节对应太多字”。
5. **一半以上的失败是模型在改写，不是在转写。** 正式流程的 382 条往返失败里，206 条（54%）多一个或少一个音节：漏掉“自己”“午”，把“我怎会”写成“我怎么会”，“逛个街”写成“逛逛街”，“领先位置”写成“领先地位”。提示词里写着不增字不删字，它照样做。带声调时这一类仍然是最大的（234 条失败里 102 条是漏音节）。
6. **其余的读错分两种。** 一种是专有名词上用世界知识顶替读音：`歼16跟歼11` 写成“16斤和11斤”，`后窗、惊魂记、西北偏北` 写成“话好好说、荆轲刺秦王、西伯利亚的理发师”。另一种是相差一步的看走眼：期/季、翻牌/安排、处/车。
7. **句子越长越差**，15 字以上只有 51%；没有上文时明显更差。

**修改了什么。**

- 没有改正式流程。这一轮测的都是提示词层面的因素，正式流程的提示词已经是其中最好的；明显更高的只有带声调，而那不可用。把它改成“只给分开的音节”会更差，所以不改。
- 实验脚本：修了丢字符的 bug 并补了测试（见下面“作废的一次测量”）；报表改成每条只算一次对齐，之前分组统计要十分钟，现在十秒；修了 `--taxonomy` 的参数解析。
- 新的假设，下一轮验证：既然一半以上的失败是增删音节，那么在每个位置只允许读音等于该音节的汉字（约束解码），应该能从结构上消掉这一类，并同时挡住“用别的专有名词顶替”。

### 第 2 轮：约束解码、定点重问、采样投票

**结果。** 1000 条干净子句，从第 1 轮里不带声调的最好变体出发（分开 + 严格指令 + 示例 + 上文）。采样投票只在 353 条上跑了。

| 做法 | 往返一致 | 整句全对 | 全对 + 容忍层 | 音节错误率 | 中位 / p99 耗时 |
|---|---|---|---|---|---|
| 出发点，不受约束 | 57.3% | 39.6% | — | 3.6% | 344 ms |
| **约束解码，只用词表内的字** | **99.1%** | **59.3%** | 76.5% | 0.19% | 360 / 621 ms |
| 约束解码，允许全部汉字 | 99.1% | 59.3% | — | 0.19% | 502 / 3798 ms |
| 定点重问，最多三轮 | 63.6% | 43.5% | — | 2.6% | 468 / 1581 ms |
| 采样 8 次，保留读得回的，取多数（353 条） | 81.6% | 54.1% | — | — | 2000 ms |

**约束解码**是每个请求带一条语法：每个位置只允许读音等于该音节的汉字。模型写出来的句子不可能多字、少字或读成别的音。llama.cpp 的对话接口接受这种语法（验证过：限定只能说“再见”，它就对问候语答“再见”）。

- 和正式流程的提示词（不受约束）逐条比：往返一致修对 372 条、**改坏 0 条**；整句全对修对 220、改坏 37。
- 各来源 98%–100%，21–30 字的长句 99%。不受约束时长句只有 51%。
- 没全对的 407 条里，172 条是上下文也分不出的同音写法（人名等），不计入解码器的错；作为对照，正式流程不受约束时全对加容忍层是 51.3%。
- 剩下 9 条往返失败是语法取的单字读音和逐字对齐取的词组读音不一致，多音字的边界情况。

**定点重问**是 iter-04 的修复回路换个触发条件：只要有一个音节读不回就触发，连单个没对上的字母也指出来。提示词和接受规则都是正式流程的。427 条被重问，其中 310 条（73%）没有变化。

**采样投票**是同一句在温度 0.8 下采 8 次，只保留读得回的候选，取其中最常见的。65 条（18%）8 次里没有一次读得回。

**观察到的问题。**

1. **约束解码是对 round trip 最有效的办法。** 它从结构上禁止了第 1 轮找到的两大类失败：增删音节、读成别的音。
2. **语法必须限制在常用字。** 两种规模的输出完全一样，但允许全部汉字时一句话的语法有上万字符，p99 从 0.6 秒涨到 3.8 秒，最大 18.5 秒。
3. **剩下没全对的三类，都不是约束造成的。** 同音里选错（121 条），多在成语和固定搭配上：悄无声息→巧无声息，雨露均沾→浴鹿军战，井喷→精盆。不受约束时写的是一样的。词表外的词（114 条）：人名、方言、行话、专名，“朱炳仁艺术博物馆”成了“朱秉仁医术博务观”。再加上下文也分不出的 172 条。这三类分别对应不带声调时同音字太多、词汇量、以及本来就无法决定。
4. **靠提示让模型自己改，效果有限。** 定点重问 73% 没有变化，和 iter-04 里回路产出低是同一个现象。
5. **采样投票有效但贵**，延迟是约束解码的 6 倍，还差 18 个百分点。
6. **约束解码依赖 llama.cpp 的语法接口**，远程模型的通用接口没有。定点重问和采样投票可以移植，但效果差得多。
7. **校验器的一个 bug。** 多音字的另一个读音比词组读音长时，没法整个对上：用户打 `liao de`（了得），`liao` 被当成一个多余的 `l` 加上 `iao`，多记一分。逐字对齐试的字母数只按第一个读音算。
8. **一处兜底提示的说法错误。** 列不出具体位置时提示说“超过了额度”，但只有真的超额度时才对。正式流程里只有超额度才会走到这一行，线上不受影响。

**修改了什么。**

- `verify.py`：每个字试的字母数覆盖它所有的读音，不只第一个。全量 65,280 条回归：只有 1 条变化，是注入的错误恰好落在该字的另一个读音上，现在算作看不见的错误；标准答案超出额度的仍是 16 条。之前两次 3000 条运行里约 2% 的回复代价会略降，重放确认的结果记在第 3 轮。
- `infer.py`：兜底提示只在真的超额度时说“超过了额度”。两处都带测试。
- 实验：约束解码、定点重问、采样投票三个脚本；测评脚本加了“正式流程的提示词”变体（发出的消息和正式流程完全一样）；抽样子集支持排除已用过的；报表每条只算一次。
- **没有把约束解码放进正式流程。** 带噪输入的音节序列是不确定的，语法怎么生成是下一轮要设计的。记为建议，附上面的数字。

### 第 3 轮：确认、校验器修复的重放、从按键生成语法

**结果。**

**在另一批子句上确认。** `clean-1000-b` 是另抽的 1000 条干净子句，没有用于挑选任何配置。它比 `clean-1000` 偏容易：benchmark 里 21–30 字的干净子句只有 214 条，全被 `clean-1000` 抽走了，所以它的平均长度是 11.6 字，而 `clean-1000` 是 14.0 字。两批之间的绝对数字不能直接比，各批内部的逐条比较有效。

| `clean-1000-b`，正式流程的提示词 | 往返一致 | 整句全对 | 中位耗时 |
|---|---|---|---|
| 不受约束 | 63.3% | 43.5%（40%–47%） | 326 ms |
| **+ 约束解码** | **99.4%** | **55.4%**（52%–58%） | 349 ms |

逐条比：往返一致修对 361、改坏 0；整句全对修对 119、**改坏 0**。第 2 轮的结论在没用于挑选的子句上成立。

**约束之下，哪种提示词更好**（`clean-1000`，都带约束解码）：

| 提示词 | 往返一致 | 整句全对 |
|---|---|---|
| 正式流程的：连写的按键 + 一行切分 | 99.3% | 52.3% |
| 分开的音节作为主要输入 + 严格指令 + 示例 + 上文 | 99.1% | **59.3%** |

逐条比整句全对是 124 对 54。读音有语法保证之后，模型不必再从连写字母里认音节，直接看分开的音节选字选得更准。

**校验器修复后的重放**（3000 条带噪输入，同一批首次回复）：

| | 全对 | 容忍层 | 错误上屏 | 被拦下 |
|---|---|---|---|---|
| 修复前 | 800 | 155 | 1279 | 921 |
| 修复后 | 799 | 154 | 1292 | 909 |

修复让 13 条原来被拦下的错误回复上屏，另有一条原来靠修复回路改对的没再进回路。多记分碰巧挡住了这些。修复本身是对的，保留，代价记在这里。

**语法该怎么生成：上限分析。** 约束解码只能写语法允许的字。第 2 轮里语法是按标准答案的切法生成的，那是不现实的条件：正式流程里只有切分器给的一行音节。在 3000 条带噪输入上算“正确答案能不能被写出来”，不用模型：

| 输入里的噪声 | 按切分器那一行生成 | 同上，`?` 处放宽一步 | 同上，每处放宽一步 | **按按键生成，一步之内的音节全部允许** |
|---|---|---|---|---|
| 没有噪声 | 87.1% | 87.1% | 88.9% | **100%** |
| 漏按一个字母 | 15.0% | 19.1% | 57.8% | **100%** |
| 按成相邻键 | 30.1% | 43.4% | 63.6% | **100%** |
| 句尾没打完 | 19.2% | 20.9% | 44.2% | **100%** |
| 错两处以上 | 17.7% | 23.1% | 40.1% | **100%** |
| 全部 | 50.0% | 53.3% | 66.1% | **100%** |

“按按键生成”是把语法建成按键上的一个格：每个位置允许所有能从这里开始的合法音节，每个音节通向它后面那个位置，边界由模型自己选；带一步容差时音节可以和字母差一步，句尾的音节可以没打完。

**格状语法的实测**（`clean-1000`，语法只从按键生成，不带容差）：

| 提示词 | 往返一致 | 整句全对 | 中位 / p99 耗时 | 语法大小 |
|---|---|---|---|---|
| 分开的音节作为主要输入 + 严格指令 + 示例 + 上文 | 98.5% | 51.4% | 366 / 716 ms | 中位 3.7 KB |
| 正式流程的（连写按键 + 一行切分提示） | 98.7% | 45.0% | 373 ms | 中位 3.7 KB |
| 参照：语法按标准答案的切法生成 | 99.1% | 59.3% | 360 ms | — |

- 7 条走不通（小写英文夹在拼音里，如 `rap`、`ptt`；`cm` 这样的字母组合；全角数字），回退为不带语法。
- 相比不受约束（57.3% / 39.6%），两项都大幅提升，延迟不变。
- 相比“知道正确切法”的参照，整句全对少 8 个百分点（逐条 3 对 82）：音节边界交给模型选，选错边界的就多出来。往返一致只少 0.6 个百分点。
- 约束之下，把分开的音节作为主要输入比正式流程的提示词整句全对高 6 个百分点（逐条 107 对 43）。

**带一步容差的格状语法**（带噪输入用）：

- 耗时主要取决于模型想写的字被语法拒绝的次数，不是语法的大小。提示只是一句“ke la shi”时，`kelashi` 一句要 43 秒；用正式流程的提示词（示例、上文），10–22 个字母的句子语法 14–26 KB，每条 1 秒上下。
- 要不把正确答案挡在外面，就得放进一步之内的全部音节。只留最可能的几个，上限明显下降：

| 一步之差里保留哪些音节 | 上限（3000 条带噪输入） | 漏按一个字母 | 句尾没打完 | 错两处以上 |
|---|---|---|---|---|
| 全部 | 100% | 100% | 100% | 100% |
| 切分器按击键代价挑的（`readings()`） | 84.7% | 65% | 64% | 67% |
| 最可能的 4 个 + 口音合并 | 83.2% | 58% | 59% | 65% |
| 最可能的 2 个 + 口音合并 | 77.9% | 45% | 53% | 55% |

**带噪输入上的实测**（`trial-300`，带一步容差的格状语法，正式流程的提示词）：跑到第 7 条时超过 300 秒的超时，中断。前 6 条的耗时是 1.0、1.3、3.1、0.0、1.6、1.7 秒，语法 42–45 KB；此前抽的 3 条在 1 秒以内。多数句子要 1–3 秒，已经超出输入法主路径能接受的范围，偶发的卡死更不能接受。样本太小，效果（整句全对、是否读得至少和标准答案一样好）不下结论。

**观察到的问题。**

1. **按一行音节生成的语法，即使输入没有噪声也写不出 13% 的正确答案。** 切分器只给一种切法，而音节边界有歧义：`xian` 是“先”还是“西安”。第 2 轮的 99% 是按标准答案的切法得到的，不能直接搬进流程。
2. **带噪输入的语法只能按按键生成。** 一行音节在漏按一个字母时只剩 15%。
3. **不能靠“每个位置只留最可能的几个音节”来缩小语法。** 一步之内的音节只留最可能的 2 个加口音合并，上限降到 77.9%（漏按 45%，句尾没打完 53%）；留 4 个是 83.2%；用切分器按击键代价挑的是 84.7%。漏按的字母可以是任何一个，正确的音节常常不在前几名。要到 100% 就得全留。
4. **全留的语法在带噪输入上跑不动。** 多数句子 1–3 秒，有的卡死。耗时取决于模型想写的字被语法拒绝的次数：干净的输入上模型少走弯路，同样的语法只要 0.4 秒。
5. **确认集偏容易。** 两批子句的长度构成不同。

**修改了什么。**

- `experiments/lattice_decoding.py`：按按键生成格状语法，支持一步容差、按字频限制每个音节的字数、走不通时回退为不带语法；请求超时或被拒时记为失败，不中断整次运行。`experiments/grammar_ceiling.py`：上面那张上限表。`experiments/noisy_report.py`：带噪输入上的报表，除了整句全对，还看回复读得是否至少和标准答案一样好。
- llama.cpp 的语法规则名不能带下划线，第一版格状语法因此被服务器拒绝，改成了 `r` 加音节。
- 测试：格上的每个位置通向它后面的位置；数字串、以大写开头的词原样传递；**拼音字母不能被当成一个词原样写回**；一步容差下 `la` 处可以写 `lao`；纯拼音字母而完全不是拼音的串没有出路。
- 没有改正式流程。

### 这一轮的结论

对照[目标](#目标)里的四条。

**1. 把“正确的拼音 → 汉字”测清楚了。** 1000 条干净子句，只看模型的首次回复：

| 做法 | 往返一致 | 整句全对 | 全对 + 容忍层 | 中位耗时 |
|---|---|---|---|---|
| 连写拼音，裸提示 | 8.6% | 4.3% | — | 366 ms |
| 正式流程现在的提示词 | 61.8% | 41.0% | 51.3% | 492 ms |
| 分开的音节 + 严格指令 + 示例 + 上文 | 57.3% | 39.6% | — | 344 ms |
| 带声调符号，裸提示。用户不打声调，只用来定位瓶颈 | 70.6% | 51.2% | — | 353 ms |
| 定点重问，最多三轮 | 63.6% | 43.5% | — | 468 ms |
| 采样 8 次，保留读得回的，取多数。只在 353 条上跑了 | 81.6% | 54.1% | — | 2000 ms |
| 约束解码，语法从按键生成 | 98.5% | 51.4% | — | 366 ms |
| 约束解码，语法按标准答案的切法生成。参照，实践中拿不到 | 99.1% | 59.3% | 76.5% | 360 ms |

在没用于挑选的 1000 条上确认过：分开的音节 + 严格指令 + 示例 + 上文，加约束解码，往返一致 99.8%、整句全对 61.3%，逐条比不受约束是修对 418 和 199、改坏 0。

**2. 剩余没全对的，说得出原因。** 以约束解码、参照语法为例，没全对的 407 条分三类：

- 172 条是上下文也分不出的同音写法，多是人名。不算解码器的错。
- 121 条是同音里选错，多在成语和固定搭配上：悄无声息→巧无声息，雨露均沾→浴鹿军战。不带声调时同一个音节对应的字太多。
- 114 条是词表外的词：人名、方言、行话、专名，“朱炳仁艺术博物馆”成了“朱秉仁医术博务观”。

这三类都不是约束造成的，不受约束时写的是一样的。从按键生成语法比按标准答案的切法生成还多丢 8 个百分点的整句全对：音节边界交给模型选，选错边界的就多出来。

**3. 可以放进正式流程的配置**，限于没有敲错的输入：

- 提议：分开的音节作为主要输入，连写的按键放在旁边，严格指令、示例、上文照旧。
- 约束解码：语法从按键生成（格状，不带容差），每个音节只允许词表里字频前 25 的字；走不通时不带语法重发。
- 校验和回路照旧。

它在 1000 条干净子句上是往返一致 98.5%、整句全对 51.4%、中位 366 ms。从按键生成的语法只在这一批上量过；在另一批上确认的是按标准答案的切法生成的语法。**还没有放进正式流程**，记为建议。带噪输入目前没有可用的配置。

**4. 这个模型够不够用。**

- **让它自由地把拼音转成汉字，不够用。** 没有敲错的输入也只有 62% 读得回，提示词怎么写都上不去。
- **放在约束解码里当语言模型，够用。** 读音由语法保证，它只负责在读音相同的字里选。干净输入上整句全对 51%–61%，加上下文分不出的写法是 76.5%。
- **换更强的模型主要帮的是选字**，成语、搭配、词表外的词；对“读得回输入”帮助有限，因为那是生成方式的问题，不是能力的问题。

**没能回答的。** 量化版本的影响（Q7）需要下载，没有做。

### 作废的一次测量

第一次在 1000 条上跑的时候，脚本生成拼音用的是 pypinyin 的 `lazy_pinyin(..., errors='keep')`。在这个版本里它的行为和 `errors='ignore'` 一样，并不保留非汉字字符，标点、数字和英文全被丢掉了。模型没看到句号和 `HR`，评分时又拿完整的按键去比，于是不带示例的四个变体只有 1%–8%。这组数字是无效的，已经作废并重跑。修正后的脚本把中文段落转成读音、其它字符原样保留，并验证过连写形式和按键逐条相同（1000 / 1000）。
