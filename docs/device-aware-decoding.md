# 设备感知的噪声输入

## 基本假设

用户实际输入的字符不是用户意图本身，而是经过设备和操作习惯影响后的观测结果。

```text
用户意图
    |
    v
拼音和混合文本
    |
    v
键盘、触摸屏和个人习惯产生噪声
    |
    v
系统观察到的原始输入
```

因此，解码目标不是简单的字符串纠错，而是估计：

```text
P(intent | observed_input, device, context)
```

## 相邻键误触

在 QWERTY 键盘上，某些替换具有更高的可能性：

```text
a -> s
n -> m
r -> t
i -> o
```

例如：

```text
xiang -> xisng
xian  -> xiam
```

其中：

```text
a -> s
n -> m
```

都是相邻键替换。系统不应把它们视为与随机字符替换相同的错误。

## 音节块转置

并非所有错误都来自键盘位置。例如：

```text
shurufa -> shufaru
shu ru fa -> shu fa ru
```

这更接近局部音节块转置。模型需要同时支持：

- 字符替换
- 字符漏失
- 字符重复
- 字符插入
- 字符交换
- 音节块转置
- 拼音边界不明确

## DeviceProfile

设备信息应该作为推理请求的一部分：

```json
{
  "form_factor": "physical_keyboard",
  "keyboard_layout": "qwerty",
  "locale": "zh-CN",
  "platform": "linux",
  "touch_input": false
}
```

移动设备需要进一步描述：

- 键盘尺寸
- 触摸区域
- 输入法布局
- 滑动输入状态
- 设备方向
- 用户触控偏移

## 混合解码策略

推荐使用混合架构：

```text
原始字符流
    |
    v
设备感知的候选修复
    |
    v
拼音切分和合法性约束
    |
    v
LLM 结合上下文进行意图排序
    |
    v
输出校验和置信度决策
```

设备模型提供“哪些错误更可能”，语言模型提供“哪种完整表达更合理”。二者不能互相替代。

## 研究问题

- 如何自动识别用户当前键盘布局？
- 如何为不同设备建立错误概率矩阵？
- 如何区分真实英文和拼音片段？
- 如何在不增加明显延迟的情况下运行长上下文模型？
- 什么时候应该直接提交，什么时候必须等待确认？
- 如何在本地学习用户习惯而不上传原始输入？
